# PulseFeed 中文文档

[English](../README.md) | 中文

**面向实时事件流的事件触发式 LLM Timeline Feed。**

---

## 核心观点

LLM 推理是一种**昂贵、有限、且会失败**的在线资源。它不应该是每条数据都必须经过的一个步骤。

PulseFeed 把「调用 LLM」当作一个**在线控制动作**：针对每个事件单独决策，依据是剩余预算、当前队列深度、以及这个答案还能保鲜多久 —— 而不是无条件地对所有事件调用。

没有被 enrich 的事件**仍然会立刻**成为一条排序过、去重过的 timeline 条目。所以彻底失去模型，损失的是 feed 的文字表述，而不是它的内容。

## 系统结构

```
事件源
  │
  ▼
流式接入 (Redis Streams，at-least-once，显式 ack)  ← 永不阻塞在 LLM 上
  │
  ▼
廉价特征提取  (100% 流量，9 个特征，无网络调用)
  │
  ▼
合并 / 去重   (同实体 + 时间接近 + 文本相似)
  │
  ▼
触发 / 准入策略  (utility vs 随预算、负载、时效变化的阈值)
  │            ╲
廉价路径      LLM 路径
  │             │
  │        有界优先级队列 (P0..P3，加权公平 8:4:2:1)
  │             │
  │        语义增强 (熔断器、重试预算、时效感知重试)
  ╲            ╱
   ── 实体记忆 ──
        │
   排序 / 聚类
        │
   层级摘要 (event → micro → cluster → episode → digest)
        │
   用户 Timeline (每一行都能展开成原始事件)
```

## 两条不变量

整个系统的其他部分都是这两条的推论。

### 1. 原始事件是唯一真相；模型输出只是标注

> 原始 `Event` 是 canonical truth。模型产生的任何东西都是一个 `SemanticAnnotation`，它**引用**事件 id，**永远不修改也不替换**事件本身。

推论：

- 一条幻觉出来的摘要，只是**贴在完好事实上的错误意见**。每一行都能展开成它的证据（`GET /v1/items/{id}/evidence`）。
- `source_event_ids` 会被校验为「这次调用提供给模型的 id 集合的**子集**」。模型无法把输出归因到它没见过的事件上 —— 包括**别的租户**的事件。伪造的 id 会被剥离**并计数**。
- 失去 provider，损失的是摘要，永远不是事件。

### 2. 接入路径永不等待 LLM

`ingest()` 打分、合并、决策、返回。它不打开任何 socket。

没被准入的 cluster 立刻成为一条 timeline 行；被准入的 cluster **也**立刻成为一行 —— enrichment 落地时**原地升级**这一行。所以 feed 在任何时刻都是完整的。

## 实测结果

在一条 6,396 事件 / 15 分钟模拟时长的种子化轨迹上（`python -m harness.replay`，可复现）：

| 方案 | LLM 调用 | 成本 | recall@10 | recall@20 | 读到 80% 需要几行 | 峰值队列 |
|---|---|---|---|---|---|---|
| A. 纯时序 | 0 | $0 | 7.9% | 7.9% | 4,903 | 0 |
| B. 规则+embedding | 0 | $0 | 26.3% | 52.6% | 47 | 0 |
| C. 全量 LLM | 4,905 | $3.33 | 44.7% | **94.7%** | 20 | 1,748 |
| **D. PulseFeed** | **51** | **$0.055** | **84.2%** | 84.2% | **9** | **2** |

**诚实地读这张表：**

- **比全量 LLM 少 99.0% 的调用（51 vs 4,905），成本只有 1.6%。**
- **PulseFeed 在「滚动深度」上大幅领先**：读 9 行就能覆盖 80% 的重要事件（C 需要 20 行，B 需要 47 行）；覆盖 95% 需要 31 行，而 C 需要 **419 行**。一个 episode 行承载整个事故，而不是用二十行来讲。
- **全量 LLM 在 recall@20 上仍然赢（94.7% vs 84.2%）。这是真实的损失，不是度量假象** —— PulseFeed 的排序头部有相关行，然后出现断层。这是排序器目前最弱的地方。
- **全量 LLM 跟不上**：队列堆到 1,748，p99 等待 74 秒，1,500 条在被处理前就因过期被丢弃。PulseFeed 队列峰值是 2。
- **PulseFeed 覆盖 80% 的植入故事线，C 覆盖 100%。** 准入控制确实会漏东西。这是被**测量**出来的取舍，不是被断言的。
- **完全没有 LLM 时**（方案 B —— 也就是 provider 彻底挂掉时的真实行为），feed 仍然达到 52.6% recall@20 和 100% 总覆盖。

## 故障注入：7/7 通过

`python -m harness.failure_injection`

| 场景 | 断言了什么 |
|---|---|
| provider 宕机 | 宕机**期间**仍产出 557 条；熔断器打开；恢复后 enrichment 自动恢复 |
| 50 倍突发流量 | 实测负载 3.3 → 151.5 事件/秒（**45.6 倍**），enrich 速率只从 0.025 升到 0.235/秒，15,872 条被合并，**峰值队列深度 0** |
| 负载卸载 | 剥掉负载感知、饿死容量后：P2/P3 队列打满并卸载 89 条 P3，**P0 和 P1 从不被丢弃** |
| 慢 provider | 82 次被时效策略拒绝准入；熔断器保持 **closed**（这是「慢」路径，不是「宕机」路径） |
| 投毒事件 | 密钥不进 prompt；分隔符被中和；伪造引用被剥离并计数；模型编造的字段被丢弃 |
| broker 中断 | 120 秒中断期间缓冲并重放 5,017 条事件，零丢失 |
| 消费者崩溃 | 一个消费者持有 100 条未 ack 的投递后死掉，另一个全部接管；2,657 发布 → 2,657 接入 |

## 安全立场

Feed 内容**按定义就是不可信输入** —— 任何能在被监听频道发言的人，都能把文本送到模型面前。防御是**结构性的，不是靠说服的**：

- 事件以带分隔符的**数据**形式渲染，内容里像分隔符的序列会被中和（`</event>` → `‹/event>`）；
- 「以下是不可信数据」的说明**紧挨着数据重复一遍**，不只放在 system prompt 里 —— 注入攻击惯用的手法就是利用「顶部的规则」和「下方的敌意文本」之间的距离；
- 密钥在**进入**方向就被脱敏，永远不到达 provider；
- 响应 schema 固定并校验：未知枚举回退、数值裁剪、列表限长、模型编造的字段丢弃；
- **不暴露任何 tool**，所以没有东西可以被调用。动作只被**建议**（`actionability`），从不被执行。

注入成功的最坏后果，是在一堆正确、可检查的事件之上出现一条错误的摘要。

## 已知局限（明确列出）

1. **轨迹是合成的。** 标签由构造产生（PulseFeed 从不读取，mock provider 从不看见），但流量形态是我们自己选的。
2. **mock provider 不是语言模型。** 它做真实的分析（读 cluster、用实体记忆、识别 deploy→劣化→回滚 的顺序），所以 LLM 组的优势来自真实的结构性事实；但它的文字是机械的，**这里没有任何东西测量了摘要质量**。
3. **K=20 上排序落后**（84.2% vs 94.7%）。已诊断，未修复。
4. **学习版 scorer 从未见过真实流量，也从未在 GPU 上跑过。**
5. **单进程。** 按 `tenant_id`/`entity_id` 分片是设计意图，不是运行中的代码——今天什么能扩、什么不能，在[部署指南 §10](deployment.md#10-扩展的边界加副本之前必读) 里写得很清楚。
6. **认证默认关闭。** 设置 `PULSEFEED_API_KEYS` 后，**key 决定租户**（绑定 `acme` 的 key 无论请求体怎么声明都只能作为 `acme` 行动），并按租户做读写分离的令牌桶限流（超限 429 + `Retry-After`）。不设置则是全开的开发模式 —— `/readyz` 会明确报告这一点，因为一个裸奔的公网部署不应该看起来和正常配置一模一样。

## 与原 Timeline-Feed 项目的关系

本仓库原有一个 TypeScript/Express 社交 timeline —— 关注图、Kafka 推拉混合 fanout、Redis sorted-set 时间线、MongoDB 持久化。那个服务**未被改动**，仍然可以构建；PulseFeed 并列存在于 `pulsefeed/`。

继承下来的是**架构骨架**（ingest → queue → worker → store → read API，外加指标），以及一个意外有用的东西：Redis sorted set 按 timestamp 打分**就是**时序 feed，正好是实验方案 A。

没有继承的是所有领域相关的东西 —— 当处理单元是「关于某个实体的事件」而不是「某个用户发的、被读者关注的帖子」时，关注图没有对应物。选 Python 是因为目标技术栈（asyncio、FastAPI、pgvector）是 Python，而且这里的工作是 I/O 密集的编排。
